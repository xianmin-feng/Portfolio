Spatial UI Component Library

Building a reusable design system in Unity that became the shared language for prototyping across Horizon OS.

Summary

As the number of prototypers and designers working on Horizon OS grew, so did the inconsistency. Each person built their own buttons, cards, and panels from scratch — different spacing, different text hierarchies, different interaction behaviors. Prototypes looked different depending on who built them, and every new project started from zero.

I designed and built a component-based UI library in Unity — a set of composable primitives with built-in design decisions (typography hierarchy, spacing, interaction states, visual treatments) that any designer or prototyper could drop into a scene and start building with immediately. The library became the team’s shared infrastructure, adopted by 40+ people across the organization.

01

The Problem — Inconsistency at Scale

When every prototyper builds UI from scratch, the results diverge. Buttons look different across prototypes. Card layouts use different spacing. Text hierarchies vary. For leadership reviews, this inconsistency becomes noise — reviewers spend time noticing visual differences instead of evaluating the interaction being tested.

The team needed a shared set of building blocks that enforced design consistency at the implementation level — not through guidelines people have to remember, but through components that are correct by default.

Components that are correct by default.
02

The Library — Composable UI Primitives

I designed and implemented a component library with a clear architecture:

Primitives. OCBase, OCButton, OCIcon, OCIconButton, OCImage, OCText — the foundational elements that everything else is built from. Each primitive carries its own styling, states, and interaction behavior.

Composed components. OCCard, OCTile, OCMenu, OCMenuBtn, OCPanel, OCCheckbox, OCStars — higher-level components assembled from primitives. A Card, for example, combines an image area, a Primary/Secondary/Tertiary text hierarchy, and an action row — all with consistent spacing and visual treatment built in.

Examples scene. A documented scene where every component is instantiated and visible, serving as both a reference and a testing ground for new additions.

03

Design Decisions Built Into Code

The library isn’t just a collection of prefabs — it encodes design decisions that would otherwise live in a spec document no one reads:

Typography hierarchy. Every component with text enforces Primary, Secondary, and Tertiary levels — consistent font sizes, weights, and colors across every surface. Designers don’t choose type styles; the component chooses for them.

Spacing and layout. Padding, margins, and content spacing are built into each component, ensuring visual consistency without manual adjustment.

Interaction states. Hover, focus, pressed, and disabled states are implemented in the component itself. Every button, tile, and card behaves the same way across every prototype.

Composition over configuration. Rather than building one mega-component with dozens of options, the library uses small, focused primitives that compose together. Need a card with a different layout? Combine OCImage + OCText + OCButton in a new arrangement — the pieces already work together.

The same architecture as a web component library — in Unity.
04

Adoption & Impact

40+ designers and prototypers adopted the library across the Horizon OS team. What changed:

Faster prototyping. New prototypes no longer started from zero. Designers could drop components into a scene and start building immediately, focusing on the interaction being tested rather than rebuilding basic UI.

Visual consistency. Prototypes built by different people looked like they came from the same system. Leadership reviews focused on the design question, not on visual discrepancies between prototypes.

Lower barrier to entry. Designers who weren’t strong Unity developers could still build high-fidelity prototypes by composing from the library. The components handled the implementation complexity.

A shared language. The component names (OCCard, OCTile, OCButton) became vocabulary the team used in design discussions. “Use an OCCard with a secondary label” meant the same thing to everyone — design intent and implementation were the same artifact.

Closing Thoughts

Design systems aren’t about the platform — they’re about the architecture. Whether the components are React elements, SwiftUI views, or Unity prefabs, the principles are the same: composability, consistency, encoded design decisions, and documentation through examples. Building this library in Unity taught me that design system thinking is portable across any medium.

The most rewarding outcome wasn’t the adoption number. It was hearing a designer say “I built this prototype in an afternoon” — something that would have taken days before the library existed. That’s the real measure of a design system: not how many components it has, but how much it accelerates the people who use it.
